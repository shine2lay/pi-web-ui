## Files and records

`UsageWeekStore.open({ dataDir, lease })` owns `dataDir/usage-week/` (normally `~/.pi-web-ui/usage-week/`):

- `lock`: lifetime writer's PID, using the existing `GuardFileLock`.
- `week-YYYY-MM-DD.log`: header, then append-only numeric attempt/gap records.
- `week-YYYY-MM-DD.receipts`: header, then W2 first/same-call lookup receipts.
- `week-YYYY-MM-DD.checkpoint`: #304 file cursors, W2 ledger cursor, byte lengths/counts/SHA256 for log, receipts, observations and optional adjustments, and the unobserved count; its own SHA256.
- `week-YYYY-MM-DD.observations`: header, then append-only typed observations (Ops #500, below).
- `week-YYYY-MM-DD.sealed`: frozen week/subject totals, rate-version counts, coverage and sorted 16-byte key digests, lengths and SHA256.
- `week-YYYY-MM-DD.adjust`: header, then append-only late records for a sealed week.

The log, receipts and adjustment headers are `usage-week-log/1` with a `kind` and week; the observations header is `usage-week-observations/1`. The checkpoint format is `usage-week-checkpoint/2`; a `usage-week-checkpoint/1` week (written before Ops #500) still reads, as a legacy numeric-only week (below). The sealed format is `usage-week-sealed/1`. Any other version is unavailable (`store-version`), not empty, not silently converted. JSON is deterministic. Appended lines begin with the fixed key field so reload can index a SHA-proven prefix without parsing every value twice.

A record has exactly `k,d,at,src,off,len,sub,usd,tok,rate`:

- `k`: SHA256 of B3's stable attempt key; a gap needs a stable file-position key too. The first record per key wins. B3 must finalize a disposition before committing it; this format does **not** replace an unresolved record with an original under the same key. A later resolution protocol would need a deliberate format change.
- `d`: `original`, `alias`, `unverified`, `unresolved` or `gap`. Counts retain all five; only originals contribute money/tokens. Gaps require positive skipped bytes and null amounts/tokens/rate. Unknown amounts and token counts remain separately counted, never silently known zero.
- `at`: canonical UTC timestamp, assigned to a Pacific Monday week. `src`: 16-hex source-file digest; `off`: byte offset; `len`: source line size or skipped bytes. The store never opens a source chat.
- `sub`: role/project/initiative identifier links, plus optional task queue digest/number/addedAt. `usd`: exact contract decimal, up to 12 fractional places, **not a float or rounded integer micros**; this preserves sub-micro amounts. `tok`: input/output/cache-read/cache-write counts (each safe integer or null); `rate`: bounded version identifier or null.

M6's disposition and byte-length fields make the measured typical record **390 B**, rather than the route sketch's ~334 B. Maximum record line is 1,024 B. Unknowns and gaps are retained as usage detail too.

Receipts have exactly `k,kind,r`. `ledger-native` stores W2's validated `LedgerNativeReceipt` unchanged; `same-call` stores its `LedgerSameCall` canonical fact and evidence identifier under `sha256(JSON.stringify([provider,responseId]))`. No chat text or raw source path is copied: only closed numeric/identifier contract fields. `receipt(week,kind,key)` returns the reader object or proven absent `null`; an unloaded/unavailable week throws, so callers must not turn that into absence. W2 can attach an alias to a native receipt once (`alias: null` to a valid alias, all other fields unchanged); other changes are refused. Both kinds can share a key. A receipt is one W2 itself takes back (Architecture HOME F3): besides the contract's validity, the checks W2's `receipt()` and `sameCall()` make without their reader's projection are made on append, adjust and return. A native receipt's fact is pi's own (`producer: "pi"`), revision 0, `source.event` `response:<key>`, coverage `partial`, with no task or run link; a same-call original is a `verified` pi or acp fact. Otherwise `invalid-receipt`; on return `receipts-corrupt`. The checks that compare with the projection (same-call ids, provider, model, kind, time, tokens, amount) stay W2's: a stored receipt is not that proof. Like a record, a receipt belongs to the week its call happened in (Architecture HOME F2): the native fact's `occurredAt`, or the same-call original's, must fall in the week's half-open bounds. Otherwise append and adjust refuse it as `wrong-week` and a stored one is `receipts-corrupt` on return; there is no lookup in another week. Receipts are indexed by kind/key and read at their byte offset on demand, not all held as fact objects in memory.

## All observations (Ops #500)

The observations log keeps every typed row B3 actually has, for B3 to replay later instead of re-reading chats. W2's receipts stay exactly as above: an observation is not a receipt and never stands in for one.

Each line has exactly `k,o,p,rk,r`, in that order:

- `o` and `r`, the kind and its row: `fact` (`UsageFact`), `allocation` (`Allocation`), `alias` (`IdentityAlias`), `root` (`DispatchRoot`), `policy` (`ReportingPolicy`), `membership` (`TaskMembership`), `snapshot` (`RunSnapshot`) and `coverage` (`SourceCoverage`), each checked alone by the contract's own `parseAccountingInput` (closed fields, no free-form bags); and `fact-role`, W5's role witness `{ factId, role, evidenceRef }`, with `factId` a contract fact reference, `role` null or W5's role pattern and `evidenceRef` a contract reference. The contract has no parser for that witness, so the store checks its shape itself; that is not W5's own check of a witness. The row is stored canonical (sorted keys), printable ASCII only, at most 256 KiB per line. The store never builds, fills in or changes a row: a row the contract refuses is refused (`invalid-observation`), not repaired, and no provider, model, kind, `responseId`, identity or funding row is made up. An unresolved fact, or one without a `responseId`, is kept as the contract row it is.
- `k`: SHA256 of canonical `[o, row]`, where a fact's `source.observedAt` counts as null for the key only. The same kind and row again (a fact revision read again later included) is a duplicate: counted, not written, and the first committed line stays with its own `observedAt` and binding. Different content under one contract identity (another revision, or a conflicting role witness) is kept as its own line; the contract's revision rules and W5 decide between them, the store never picks.
- `p`: `open` when appended while the week was open, `late` when appended to a sealed week by `adjust`.
- `rk`: the key of the numeric record the observation came with, or null for a row bound to no record. It must name a record in the same call or one the week already has (an open week's log; a sealed week's sealed digests or adjustments), else `invalid-observation`. Nothing is copied from the record, so nothing is kept twice where it could disagree. In an open week, the record's disposition, source and offset are read from the numeric log by `rk` (reload's `each`, `"log"`; the log keeps the first record stored under a key). After the seal, reload replays only adjustments: an `rk` that names a sealed record proves the record was committed (the sealed key digest), but its disposition, source and offset can no longer be read through the store. A caller that needs them joins them before the seal; an offline audit can hash the retained log against its stored SHA256.

A fact belongs to the week its call happened in: `occurredAt` outside the week's half-open bounds is `wrong-week`, as for records and receipts. Other kinds are the context of the week they are appended to and have no time check. The store does not check which week a context row belongs to, and a week replays only the rows filed in it. So a caller files each context row in every week whose facts need it (for example, a role witness goes in its fact's week), because W5 refuses what a week's replay lacks. A record with no fact (an unverified line without evidence, a gap) stays the typed gap it is in the numeric log: no observation is made up for it.

The checkpoint (`usage-week-checkpoint/2`) adds `observations` (length, lines and SHA256 of the committed prefix; null until the week has the file) and `unobserved`. One atomic checkpoint commits the numeric log, receipts, adjustments, observations and cursors together: a crash at any point before its rename leaves the previous checkpoint, and reload cuts every log back to it. `unobserved` counts committed original records that came without a newly written fact bound to them in the same call; it never goes down.

`observationCoverage(week)` says what a loaded week's committed observations cover:

- `complete`: a version 2 checkpoint, or nothing committed yet, and `unobserved` 0. Every committed original record has its fact line, and every committed observation is proven by the checkpoint. Only originals are counted: an alias, unverified, unresolved or gap record without a fact leaves the week `complete`. `complete` covers the relations between committed records and facts, not every call that happened upstream.
- `partial`: a version 2 checkpoint with `unobserved` above 0.
- `legacy`: committed by a `usage-week-checkpoint/1` (B2 before Ops #500). Numeric only: its observations are unknown, not none. It still reloads, answers receipts, reads sealed totals and can be sealed, but append, adjust, checkpoint and replay are refused (`legacy-week`), because any new checkpoint would claim coverage the week never had. No backfill, re-read or migration happens here.

`complete` cannot prove that the caller passed a fact for every non-original record (only the caller knows whether it parsed one). B3 passes every fact it parses, bound to its record. Send each fact once, with its record, in the same call. A line's key has no `p` or `rk`, so a fact first stored without its record and sent again with it is a duplicate, and that original stays unobserved.

`observations(week, from?, rows?)` replays the committed observations in file order, in pages of at most 4,096 rows and 4 MiB read, never past the last checkpoint. A page's `next` is good only for the next page of the same stream; any other cursor is refused (`invalid-replay`), and `from` null starts again. Each line is parsed and rebuilt to the same bytes (else `observations-corrupt`), the file's identity and size are pinned on every page, and the stream's running SHA256 must equal the checkpoint's at the end: only then is `next` null. A mismatch makes the week unavailable (`observations-mismatch`), so a stream that did not end with `next` null must be thrown away. Pages before the end are provisional. Lines are checked one at a time (parsed, rebuilt to the same bytes, key), and that cannot see a changed `p`, `rk` or fact `observedAt`, or committed lines swapped in place; only the SHA256 at the end can. So a caller keeps the pages aside and uses none of them (attribution, totals, cursors) until the stream ends with `next` null, and throws them all away on an error. Every page carries the coverage.

Reload proves the observations like receipts: SHA256, length and line count against the checkpoint, unique keys read at their fixed place, and the bytes past it cut (reported as `coverage.dropped`). A missing named file is `observations-missing`, a mismatch `observations-mismatch`, damage `observations-corrupt`, another version `store-version`: the week is unavailable, never empty.

## Calling and committing

All operations are synchronous and **worker-only**, matching W0's meter-worker resource fence. Main-thread open reports `worker-required`. The host supplies one four-byte `SharedArrayBuffer` for each data directory, shared across every generation of its worker. Do not make a fresh lease to displace a worker that may still exist. A separate process is excluded by the PID lock; a stale dead process can be recovered, a live PID (including our own PID) is never evicted. Waiting returns `waiting-for-previous-writer`. Ownership is rechecked before every write/rename, not only when opening.

1. Open and check `status()` is ready. `listWeeks()` reports week files, abandoned scratch, quarantine and unexpected entries, without deleting them.
2. `reload(week, each?)` validates that week before giving any records to `each(record, "log" | "adjust")`. It returns `empty`, `open`, `sealed` or `unavailable` with a content-free code. Use `sealedTotals(week)` for historical totals without reloading old record or receipt indexes. Avoid retaining all history in one worker's loaded-week cache.
3. `append(week, records, receipts?, observations?)` validates the **entire** bounded batch, dedupes it and appends+`fdatasync`s the new lines. It does not advance source cursors. Then `checkpoint(week, { files, ledger })` commits lengths, hashes and cursors together. A receipt-only or observation-only commit is supported: the main log's header is written before the first receipt or observation (Architecture HOME F1), so a first batch of them alone, cut after they synced, reloads as an open week with nothing committed, not as a missing log. An unchanged checkpoint is idempotent. With `observations` given, the result also has `observations`, `observationDuplicates` and `unobserved`; without it, B2's result is unchanged.
4. On reopening, hash exactly the checkpointed bytes, check lengths/counts, build keys and receipt offsets, then cut every file back to its checkpointed length and `fsync`. Without a checkpoint, keep only headers. `dropped` reports **bytes** discarded from records/receipts; the observations' are in `observationCoverage(week).dropped`. Synced but uncommitted records, complete lines, torn lines, receipt and observation tails are all discarded together. Resume source reading from the returned checkpoint. Commit first, publish its totals/cursors second.
5. `seal(week, coverage)` requires that the Pacific week has ended and the current log/receipts/observations are checkpointed. It folds originals exactly, preserves disposition and unknown counts, and refuses complete coverage if unverified/unresolved/gap records remain. It writes the sealed totals and sorted truncated key set atomically; the log and receipts are retained. A repeated seal is refused as `sealed`; read the existing result with `sealedTotals`.
6. `adjust(week, records, receipts?)` accepts late attempts only for an already sealed week, dedupes against the base sealed keys and adjustment keys, then appends+syncs and writes its checkpoint before returning. Publish only after that succeeds. It never rewrites base sealed totals; readers combine base with committed adjustments. Post-seal receipts remain checkpointed alongside adjustments, and so do post-seal observations (`adjust(week, records, receipts, observations)`, marked `late`).
7. `close()` releases descriptors, PID lock and this store's held lease. On uncertain worker death the host must not forcibly clear the lease. `quarantineWeek` is an explicit corruption-handling operation, not automatic repair; it renames damaged files aside, retains their bytes and lets that one week be rebuilt later from source. No production caller is added here. `deleteWeek` exists and is tested on synthetic data **but is never called by production code**. No retention policy or deletion run is authorized.

The SHA256 proof precedes `each`, so a late hash mismatch never hands the caller a plausible partial total. A SHA, size or version failure marks just that week unavailable; its bytes stay for diagnosis and other weeks can proceed. General I/O, unsafe paths or lost ownership stop the store until it is reopened. Refused arguments write nothing and leave it ready. Zero is returned only for a genuinely empty/known zero count, never as the substitute for an unavailable week.

Sealed history reads prove the sealed totals/key digest, not the old numeric log's contents. `reload` of a sealed week checks the old log's recorded length and its header (Architecture HOME F4: another version is `store-version`, another week's or a damaged header `log-corrupt`), proves its receipt prefix and live adjustments and uses the sealed keys; `seal` itself proved the full numeric log. A same-length later mutation of the retained base log is not detected by a totals-only history read. An offline detail-integrity audit must hash it against the stored log SHA; it must not use the history read as that audit.

## Durability and custody

Appended logs use `O_APPEND | O_NOFOLLOW`, a checked private regular descriptor and `fdatasync`. Headers, checkpoints and sealed snapshots use a random same-directory `O_CREAT | O_EXCL | O_NOFOLLOW` temp, complete write, `fsync`, rename and directory `fsync`. A crash around the seal rename leaves either the old open checkpoint or a fully verified sealed snapshot. Abandoned temps remain 0600 and are counted, not swept. The log inode is unchanged by appends/checkpoints. The checkpoint is the sole commit point; a process crash before it cannot advance either source cursor or counts.

The root is 0700, files 0600 (tested by `stat`, including with a permissive umask). Every path component is opened without following symlinks; accesses are anchored to owned directory descriptors through Linux `/proc/self/fd`. Symlinks, hard-linked files, wrong owner, unsafe parent/root replacement, bad private modes and a replaced lock are refused. These are local application-data protections, not isolation from root or a hostile writer running as the same UID. Identifiers may still be sensitive metadata; the numeric store is not anonymous data.

Bounded per-call/per-week work: 4,096 records per append, 4 MiB record bytes, 16 MiB receipt bytes; 16 KiB per receipt; 16,384 observations and 16 MiB observation bytes per call, 256 KiB per observation line (the largest page W0 hands over); 500,000 records per log; 1,000,000 receipt lines; 1,000,000 observation lines; replay pages of at most 4,096 rows and 4 MiB read; 4,096 source-file cursors and 4 MiB checkpoint; 64 MiB sealed file; 8,192 directory entries. Smaller test limits are supported; greater/invalid ones are refused. Capacity means `store-capacity`, not eviction. Sealed keys are first 128 bits of SHA256, sorted for binary search; retain full log keys. No cryptographic claim of zero collision risk. File formats/caps are code constants, not new user settings.

### All observations: tests and measurements (Ops #500)

`tests/unit/usage-accounting-week-observations.test.ts` (fixture `tests/unit/usage-accounting-week-observations-fixture.ts`) runs the real module the same way, on synthetic rows written out literally in the fixture with their expected results: a verified pi fact with a `responseId`, a verified fact without one, an unresolved fork fact with an unknown model, an alias copy with its alias row, a temper fact in two revisions with its task membership, dispatch root, allocation and run snapshot, an unknown allocation, a reporting policy, a coverage row and two role witnesses, next to an unverified attempt and a gap that have no fact. Its 106 cases (two of them opt-in):

- The literal rows replay byte for byte, in pages, to a pinned file SHA256, and no row appears for the unverified attempt or the gap. B2's log and receipt bytes stay exactly as B2's own code writes them; only the checkpoint's version changes.
- A fact read again is kept once, with its first read's time; its next revision, the same revision with other content and a conflicting role witness are kept beside it. Originals committed without their fact count as `unobserved`, and the week's coverage never turns `complete` again.
- Unknown kinds, extra fields, dangling `rk`, another week's fact and each lowered cap are refused all or none: nothing is written and the store stays ready.
- 65 crash points in five runs (a second batch on an open week, bringing the receipts' header; a new week's first batch, at each of its three header writes; an observation-only first batch; late observations on a sealed week, with an observations log and without one yet), with short writes and a crash while cutting back. After reopening, every file holds exactly the last checkpoint's prefix with that checkpoint's cursors, and running the batch again gives the same rows, hashes and coverage as a run without a crash. A torn first write commits a header-only log that replays as nothing, hash-checked.
- 25 kinds of damage (a missing file, a flipped byte, a cut, wrong header version, week or family, wrong count, SHA256 or length, `unobserved` out of range, a missing or extra checkpoint key, a version 3 checkpoint, a version 1 checkpoint naming observations, a duplicate, reordered, wrong-key, bad-row or bad-phase line, a symlink, a wrong mode) give an unavailable week or a refused replay, never a shorter replay; a torn tail and an uncommitted line are cut and counted in `dropped`.
