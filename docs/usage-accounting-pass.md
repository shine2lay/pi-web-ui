## Files

- `server/usage-accounting-pass.ts`: `openPassState(options)`, `runPass(state, budget = PASS_LIMITS)`, `buildPassInput(state, asOf, completed)`, `closePassState(state)`, `PASS_LIMITS`. Refuses to run on the main thread.
- `server/usage-accounting-pass-scan.ts`: the stat-only, resumable inventory (`PASS_SCAN_LIMITS`: 4,096 files a week, 65,536 stats a pass).
- `server/usage-accounting-pass-worker.ts`: the Worker entry. One state per Worker; a tick that arrives while a pass runs is dropped, not queued (this guard is tested on its own, without the host's).
- `server/usage-accounting-pass-host.ts`: the host side B4 will call every 30 s. It starts the Worker with `METER_WORKER_RESOURCE_LIMITS` and drops a tick while one is outstanding. Any Worker exit that `close()` did not ask for, exit code 0 included, is reported once as `worker-unavailable`, and later ticks are refused. It imports only `node:worker_threads` and the meter contract, and the import guard now checks it as a main-thread root (B4 will import it there).
- `server/usage-accounting-evidence.ts`: the producer-neutral evidence header (Architecture M9, question 2). `usage-collector-evidence/1` (W0) is unchanged. The new `usage-evidence/2` carries `producer: "week-pass"`. W5 (`server/usage-accounting-snapshot.ts`) accepts either through `supportedUsageEvidence`; its other checks are unchanged.
- `server/usage-accounting-pi-sessions.ts` (#304, admitted by the Ops lead for M11/C1/C10 only): bounded recovery past a line over 4 MiB (`pis1` cursors; `pi1` unchanged), the real bytes each read costs, and a timestamp-only hint for the next window.

## One pass

1. **Single flight (C3).** While a pass runs, `runPass` returns `busy` and does nothing. The Worker and the host both drop ticks while one is outstanding. A pass never overlaps another.
2. **Horizon.** The pass fixes its time `T` when it starts. Every read uses `observedAt = T` and `through ≤ T`. The W5 input has `asOf = T`, and its coverage claims nothing after `T`. This is our reading of M9's "asOf = end of the pass": a fixed start time keeps every row, cursor and coverage line of one pass at one instant.
3. **Weeks (C4).** The week is the Pacific week of `T`, from `usageWeekBounds` (Monday 00:00 Pacific to the next Monday, 167 or 169 hours across DST; B2's tests cover 2026-11-01). Last week still takes late rows for 10 minutes after Monday 00:00 (`graceMs`). After the grace, an entry older than the current week is history: the pass skips it, counts it and moves the cursor past it. B5's backfill owns history. After the grace, the pass also drops last week's in-memory fold and reopens the store, so the store no longer holds that week (it keeps every week it loaded until it is closed). A restart after the grace keeps only last week's checkpoint.
4. **Store.** The pass opens B2's week store with the host's lease. If the store is not ready, the pass reopens it once. If it is still not ready, the status is `unavailable`, never zero.
5. **Catching up.** A new state first reloads the week's hash-checked records and receipts. It then replays the committed observations in pages of 4,096 rows, inside the pass budget. Until that is done the status is `catching-up` and no source is read. Only the identity keys, record keys, fact ids and the links W5 needs stay in memory. The W5 rows themselves do not.
6. **Inventory (PLAN 5.1, S1).** A stat-only walk of the session roots. It is resumable, at most 65,536 stats a pass, and never reads file contents. It takes only `*.jsonl` regular files with a single link, owned by the user, modified in the current week (a file already tracked stays tracked). It never follows a symlink, and it walks each directory (`dev:ino`) once. It skips the native, source-owned Temper worker roots it is given (T0 owns them), and never decides that from a name. A session root at or inside a Temper root is refused (`usage-pass-inventory-input`), since it would otherwise scan to a healthy-looking zero. The cap is 4,096 files a week: past it the inventory is partial (`file-cap`), never silently complete. Unsafe entries (`unsafe-source`), unreadable directories and tracked files that disappear (`missing-source`) also leave it partial. These four reasons stay inside the Worker's inventory. The meter sees one `inventory-partial` count for each pass whose walk is not complete, and the sessions stream is `partial`. It does not see which reason, or how many files. There is no cap alarm (PLAN.md:410 names one): see the open points.
7. **Reads (C1, C2, C10, M8, M11).** Only files whose size or mtime changed since their last end of file are read, through the #304 reader and its saved cursor. A file that ends in a partial last line, or inside an unfinished line over 4 MiB, waits until its size or mtime changes; only a file waiting on event time is checked again every pass. One read runs at a time. A pass has 64 MiB and 2,000 ms of work. It yields every 25 ms, and it starts a read only if the read's worst case (`readWorstBytes`: three 4 MiB lines, two 256 KiB budgets and 64 KiB, about 12.6 MiB) still fits. The chat files get four fifths of the work time. A reader instance is renewed before 64 files or 10,000 entries. An entry outside the window moves the file to the window of the reader's hint: the next week forward, last week within the grace, history before that, or waiting (`event-time-order`) if the hint is after `T`. A line over 4 MiB is skipped over bounded reads and recorded as one unknown gap. It sticks neither the cursor nor the pass: when the long line is still unfinished at the end of the file, its gap is recorded once and the file waits for growth, so the other files and the ledger tail are read in the same pass (Architecture #277 MF2). The gap stays: the sessions stream stays `partial` and its complete-through does not move, in later passes and after a reopen.
8. **Cursor faults (M7).** A cursor the reader refuses (`cursor-changed`, `cursor-invalid`, `source-truncated`) is dropped, and the file is read again from byte 0 within the budget. Record keys dedupe what was already committed, so nothing is charged twice. The fault is counted (`cursor-conflict`, `truncated-source`), and the pass is `partial` for that pass.
9. **Ledger tail (M10).** The usage ledger is read only once the chat files have no backlog in this pass, so ledger rows don't run ahead of the chat entries they match. It is read through W2 `readUsageLedger` in Pacific-week windows, from its cursor. W2's `first(key)` is answered first from this pass's own staged ledger-native receipts that are not yet appended, then from the store's hash-checked `ledger-native` receipt. W2 remembers its own proposals only within one call, and a pass makes several calls before it commits; without the pass's own map, a repeat in a later call would make a second "first", and the store would refuse the commit (Architecture #277 MF1). The map is cleared once the receipts are appended. A week that is not loaded (history) gets readers that answer null; its rows go to history and are never folded, so W2's "null is a proven absent key" never charges from them. `sameCall(provider, responseId)` is answered by the store's hash-checked `same-call` receipt, which the pass writes for every session original that has a response id. At the end of a month's file the cursor moves to the next month. A steady pass with an unchanged ledger file reads no ledger bytes.
10. **Fold.** Each observation gets a record key: response entries `sha256(JSON.stringify([provider, responseId]))` (the W2 key), other entries `sha256(JSON.stringify(["entry", entryId, entryTimestamp]))`, ledger rows from the ledger's own key. The entry key knowingly replaces M7/M8's header-scoped keys (`[header id, entryId, entryTimestamp]`, and the parent's header id for a copy in a child file). Copies (forks and resume copies, at any depth) and header migrations keep the entry id and timestamp but not the header id, so the wider key dedupes them where a header-scoped key could miss them. A false merge would need two unrelated sessions with the same entry id and the same millisecond: with the same numbers it is an alias, with other numbers a conflict gap, never a second charge. Architecture #277 (D2) read the change as sound. The reader's own fact id still includes the header id. A key not seen before is recorded (original, alias, unverified or unresolved). A key seen before with the same numbers is a duplicate and adds nothing. A key seen before with different numbers is a conflict: an unknown gap, never a second charge. Ledger rows have no byte offset: their records use `off` = line number and `len` = null. Line faults are recorded as gaps with `off` = line and `len` = 1.
11. **Commit.** Rows are staged in units: a record, its observations and receipts together. A pass commits twice: after the chat files and after the ledger tail. A commit appends the staged units in calls of at most 2,048 units and 12 MiB of observations, then writes the checkpoint. A cursor moves only in the checkpoint written after its rows. If the pass crashes between the two, the next pass reads the rows again and the keys dedupe them. Rows for last week (within the grace) go to last week's log and checkpoint first, then this week's checkpoint takes the new cursors.
12. **W5 input (`buildPassInput`).** A `SnapshotBuildInput` with the `usage-evidence/2` header: a strictly increasing `sequence`, `asOf = T`, `storage`, `inventoryComplete`, `requiredStreams` and meter fault counts. Sources are grouped: one stream for chat sessions (`week-pass:pi-sessions:<week>`) and one for the ledger (`week-pass:usage-ledger:<week>`, only when a ledger directory is configured), each with one source status. W5 allows at most 1,024 sources, and #304 has a stream per file (2,408 in E2). A group is `complete` through `T` only when the inventory is complete, every file was read to its end with no stop, and the week has no unknown record in that group; otherwise it is `partial`.
13. **W5 partitions.** The partitions stream from the store's committed observations when W5 takes them. Facts linked by aliases or revisions go together. Each role witness follows its fact. Partitions are packed to at most 4,000 rows and about 3.5 MB of row JSON (largest measured: 3,271 rows, 3.50 MB; W5 allows 4,096 rows and 4 MiB). The store checks the observation file's SHA256 at the end of the replay. If the file changed, W5 records `index-unavailable`, the pass is marked broken, and the next pass reloads the week from its checkpoint and reports `unavailable` while the file doesn't match. An input from an earlier pass is refused once a later pass has run (`usage-pass-stale-input`).
14. **Status.** `busy`, `unavailable`, `catching-up`, `partial` (something is unknown, behind or faulted) or `fresh`. Each result has its stats: work and I/O time, bytes read, files, reads, records, history, backlog files and ledger bytes.

Role witnesses: B3 has no producer of its own. The `roleOf` option takes a verified witness and never derives one from `payerRole`. B4 wires the real one.

## Scope and safety

The week store's security scope is exactly that of [usage-accounting-week-store.md](usage-accounting-week-store.md), and this pass claims nothing beyond it. That scope excludes a hostile writer running as the same user. Same-user check-then-use windows remain: between a stat and a later open or read, the same user can change a file. This pass does not claim that every open uses `NOFOLLOW`; the shared lock helper does not. `deleteWeek` stays test-only: the pass never calls it. No diagnostic carries source contents: faults are codes and counts.

## Hypotheses (written before the change) and results

**H-B3.** The old collection path replayed history. A bounded pass that reads only changed files and the ledger tail, and commits through B2, should cost the appended bytes plus one W5 build, not the week's history. Expected: a steady pass does at most 1 s of I/O and parsing at the E1/E2 rates. Wrong if a steady pass reads bytes it already read (apart from the reader's bounded anchor checks), or if W5's build at 125k takes more than 25 s. That case would need the aggregate-input follow-up and the done_when 2 wording question (PLAN 5.6), not a fix here. The bars hold on a quiet machine: the command below, unpinned, started at a 1-minute load under 4 (Ops' decision on Architecture #282's C1). **Result: HIT on a quiet machine.** At E1 and E2 a steady pass takes 11 and 6 ms of work, with about 3 ms of I/O (the receipted run below; an earlier runner gave 28 and 32 ms, see H-B3-FIX). It reads the two appended lines plus the reader's anchor re-checks (3,894 bytes). With nothing appended it reads 0 bytes. W5 takes 15.1 s at 125k (E1), at load 3.9 falling to 3.1. Under the machine's ordinary load, W5 misses the 25 s bar (67.5 s at E1 on the little cores, Architecture #282). That is a known limit, recorded under Measurements, with what it means live. One live W5 reading at B4's install decides PLAN 5.6's follow-up.

**H-304-RECOVERY.** The #304 loop stopped at a line over 4 MiB, refused an oversized `pi1` anchor, and reported neither the bytes a read really cost nor the time that ended a window. One huge line or an out-of-order week could starve every later charge. Change: a separately typed, bounded skip state (`pis1`), committed with one unknown gap, plus real byte counts and timestamp-only window hints. Expected: a synthetic 5 MiB line between two charges is skipped over bounded reads and restarts; both charges count once, one gap remains, and a changed anchor is refused. **Result: HIT** (5 new reader tests and the 35 existing ones).

**H-304-DURABILITY**, first run: **MISS** in the fixtures, not in the code. The fixture gave B2 fractional `mtimeMs`, and the inventory test's no-payload regex mistook a directory read for a file read. Fixed in the fixtures only. **Result after the fix: HIT.** Real-store restart and crash cases keep two charges and one unknown gap, with nothing observed twice.

**H-B3-MEM** (written after E2 failed). Wrong: E2 (250k) ran out of the Worker's 512 MB, and E1 kept 248 MB after replay (about 2 KB an attempt). Evidence: the W5 rows were kept in memory as JSON (about 140 MB of E1's 248), and the store keeps every week it has loaded. Change: stream W5's partitions from the store's committed, hash-checked observations when W5 takes them; keep in memory only the links between facts; place role witnesses by order (the writer stages a fact and its witness in one unit); release last week after the grace. Expected: E1 at most about 130 MB retained after replay, E2 completes inside the Worker limits at about 260 MB or less, the fixture totals unchanged, and W5 about 3–4 s slower at E1. Wrong if E2 still fails, E1 keeps more than 160 MB, or any total changes. **Result: HIT on memory**: E1 keeps 90 MB, E2 completes with 175 MB, and every fixture total is the same. **MISS on the time estimate**: W5 got 8.4 s slower at E1, not 3–4 s (the store reads pages, parses each row and hashes the whole file). It is still inside H-B3's 25 s bar.

**H-B3-FIX** (review round 1, written before the fix). Wrong: Architecture #277 found two must-fixes in 3bf8a4a3, and #278's control run found four bites no test caught (P1, P4, P5, P6). MF1: W2's `first()` could not see the pass's own staged ledger receipts, so a repeat in a later W2 call of the same pass made a second first, and the store's refusal left the week `unavailable`. MF2: an unfinished line over 4 MiB at the end of a file made no progress, so the pass re-read it until its budget ran out, and later files and the ledger were never read. Change: a per-week map of the pass's staged ledger-native receipts, asked before the store and cleared when the receipts are appended (MF1); a read that skips without progress puts its file to wait until its size or mtime changes, the same rule now used for a partial last line (MF2, #277 S3); plus the tests the control asked for (M1–M5). Expected: the MF1 and MF2 tests fail with the fix taken out and pass with it; the tests for M1–M4 pass and catch bites P1, P4, P5 and P6; E1/E2 steady pass and W5 build within about 10% of the earlier figures (no new per-pass work). Wrong if either MF test passes without its fix, if any of those four bites is still missed, if a steady pass reads more than the appended lines plus the 3,894 bytes of re-checks, or if the timings move by more than 25%. **Result: HIT on the fixes and the bites; MISS on the steady-pass time prediction, in the faster direction.** Each MF test fails with its fix taken out, and P1, P4, P5 and P6 are each caught (see Tests). A steady pass still reads exactly the two appended lines plus 3,894 bytes of re-checks, and an idle pass reads 0 bytes. W5 stayed within 10% (15.1 s against 14.2 s at E1, 22.5 s against 23.1 s at E2), and the retained heap is the same. The steady pass, though, moved by more than 25%, downwards: 11.4 ms against 27.6 ms at E1, and 6.3 ms against 32.4 ms at E2. The cause is not established. No change in this round adds or removes per-pass work in the harness (none of its files waits for growth). The earlier figures came from a throwaway runner, these from the vitest command below. And the same code gave 3.6 ms and 11.4 ms at E1 in two runs the same night. Lesson: per-pass work is judged by the bytes and reads a pass does, which are deterministic; milliseconds only against a fixed bar (H-B3's 1 s), never between runs.

## Open points for B4 and later

- W5 grows with the week: 23 s at E2 is about three quarters of the 30 s cadence. B4 should build W5 less often than every pass, or only on demand, rather than after every pass. This is a note for B4's plan; nothing here changes the cadence. Architecture #277 (S6) projects that at the 4,096-file cap (1.7 times E2) straight-line growth would put W5 past 30 s and its heap near 460 MB: B4 should measure at the cap before load grows.
- No cap alarm. PLAN.md:410 names an alarm for the 4,096-file cap; it is not built. The meter shows the cap, like every other inventory fault, only as `inventory-partial` and a `partial` sessions stream, and the source status has `alarm: null` (the contract's only alarm is `source-stalled`). For B4 and Ops HOME to decide. Architecture's suggestion (#277 S1), not taken here: map the reasons to existing meter codes (`unsafe-source` to `unapproved-source`, `missing-source` and unreadable directories to `source-unavailable`, the cap staying `inventory-partial`), with counts kept in a map instead of a set.
- Partition sizes rely on order: the writer stages each role witness right after its fact. A witness out of order fails the W5 build closed (`usage-pass-role-order`); it is never guessed.
- Whether chat files ever have entry timestamps that go backwards was not checked on real files (AGENTS rule 11). The pass handles both directions through the reader's hint.
